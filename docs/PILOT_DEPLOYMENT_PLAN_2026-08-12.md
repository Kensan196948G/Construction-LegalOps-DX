## 🔧 3. 展開手順（人間実行）

### Step 1: 承認ゲート

1. #23 の Vault 投入手順を実行（`scripts/generate_rsa_keys.sh` → `scripts/setup_vault_secrets.sh` → 本番 env の Vault 参照切替）
2. #24 の CSP enforce（7 日間レポート確認後、`infra/nginx/security-headers.enforce.conf` を適用・reload）
3. #50 の採否決定（Cloudflare+Neon 採用 or オンプレ維持）と課金・法務判断の記録

### Step 2: パイロット環境準備（IT/DX 1 名・1 日）

1. パイロット用 Entra ID セキュリティグループ作成（`LegalOps-Pilot`）
2. ロール割当: 法務リード 1・レビュー担当 3〜5・管理部門 1・監査 1
3. テストデータ確認（過去 3 か月の実契約メタデータ 20〜50 件をレビュー用に登録）
4. 通知宛先（Exchange メール / Teams）のパイロット設定

### Step 3: 実運用（10 営業日）

| 業務 | 対象機能 | 成功基準 |
| --- | --- | --- |
| 契約レビュー | AI 一次レビュー + 法務確認 + 修正提案 | 10 件以上完了、AI は下書き・最終判断は人間 |
| 契約登録・編集 | 登録・アップロード・編集・期限表示 | 20 件以上の登録・編集エラー 0 |
| 期限管理 | 期限一覧・アラート | 期限漏れ 0・通知到達確認 |
| 法務相談 | 一次情報 RAG 検索 | 10 件以上の利用、引用先の有効性確認 |
| 監査 | 監査ログ閲覧・ハッシュ検証 | 全操作が監査ログに記録 |

### Step 4: 評価と判定（2 日）

- 定量: レビュー所要時間（目標 2 営業日以下）・操作エラー率・通知到達率
- 定性: ユーザーアンケート（NPS 目標 +30）、ヒアリング 5 名
- 判定: パイロット結果を CTO がレビューし「全社展開 / 条件付き継続 / 中止」を決定

## ↩️ 4. ロールバック方針

- デプロイは 1 リリースずつ行い、前リリースの Docker image タグを保持
- 重大障害（認証不能・データ破壊・監査欠落）時はパイロット URL を元リリースへ切替
- DB は PITR 前提（Neon branching or pg_dump 最新）で復旧手順を事前ドリル

## ⚠️ 5. リスクと緩和

| リスク | 緩和 |
| --- | --- |
| AI 誤判定 | 人間承認原則・免責表示・監査ログ・パイロット中は法務リードの全件確認 |
| 権限逸脱 | RLS + ACL + ロール割当レビュー（四半期）+ パイロット中は監査担当の週次確認 |
| 期限漏れ | 通知の到達確認・期限一覧の週次チェック |
| 本番未経験 | スモークテスト + k6 smoke + PITR ドリルを開始前に実施 |
